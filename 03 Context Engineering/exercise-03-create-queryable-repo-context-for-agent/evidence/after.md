## Findings

1. **Architecture.** Confirmed as in `evidence/before.md`: `loadRevenueDashboard()` and `publishRevenueSnapshot()` both call the shared `buildRevenueSummary()`. New this pass: `graphify affected "buildRevenueSummary()" --depth 2` surfaced a third consumer, `App()` in `App.tsx`, which calls `loadRevenueDashboard()` directly - a real dependency edge that a single-file read of `revenueSummary.ts` would not reveal, since `App.tsx` is two hops away. **Still unresolved even with the graph**: nothing in the indexed corpus (code, tests, config, or docs) shows what actually triggers `publishRevenueSnapshot()` in production. "Scheduled" is only ever a label, never a wired invocation - this is a genuine gap in the supplied corpus, not a shortcoming of the graph or the query.

2. **Dependencies.** Confirmed: both `recognizedRevenueByAccount()` and `grossVolumeByAccount()` depend on the single shared `resolveBillingAccountId()`. `docs/current-metric-contract.md` (not read in the before-pass, since that pass was scoped to `src/`) states this as explicit policy ("Every event must resolve through the tenant-to-account directory," "A missing tenant mapping is an error and must not create a fallback grouping key"), matching the code's `throw` on a missing link line for line.

3. **Data flow.** Confirmed and extended: totals are keyed by resolved `billingAccountId`, not `tenantId`, so multi-tenant-per-account grouping works as `docs/current-metric-contract.md` requires ("Totals are grouped by billing account, never by tenant"). Because both consumers call the same `buildRevenueSummary()`, a dashboard/snapshot disagreement is not currently reachable through this call path - relevant because `incidents/REV-482.md` lists exactly that disagreement as a reported symptom.

4. **Business rules.** Confirmed against `docs/current-metric-contract.md` word for word: charge = `grossAmount - credits`, refund = `-grossAmount`, gross volume untouched by either. **Resolved this pass, not resolvable in before.md**: `incidents/REV-482.md` is still marked "Status: Open" and reports the current formula's exact opposite behavior as a live bug. The graph draws only an `INFERRED conceptually_related_to` edge here (topical, from the extraction subagent reading both files together) - it does not itself resolve the contradiction. Source verification does: `recognizedRevenue.ts` line 8 and the passing `npm run test:billing` assertions (from `evidence/before.md`) directly contradict REV-482's reported symptoms. This is either an already-fixed incident that was never closed, or a stale incident doc; either way it is now a specific, named, source-backed question instead of an unverifiable guess.

5. **Ownership.** **Fully resolved this pass** - the single biggest gap in `evidence/before.md`. `docs/service-ownership.md` ("Status: Current"): Billing Platform owns the recognized-revenue formula and the tenant-to-account directory; Support Analytics consumes the dashboard; Finance Operations consumes the scheduled snapshot. Checking every older note individually (not assuming "older = wrong"): `docs/legacy-finance-metrics.md`'s dashboard-ownership claim still **agrees** with current ownership; `docs/previous-agent-progress.md`'s claim that the snapshot was "a separate calculation owned by Support Analytics" **disagrees** (current owner is Finance Operations, and it is explicitly not a separate calculation); `docs/graph-extract.md`'s claim that "Support Analytics owns calculation changes" **disagrees** (the formula itself is owned by Billing Platform). The independently-run fresh agent (see Proof) reached the identical breakdown without being told any of this in advance.

6. **Change impact.** Confirmed and extended: `graphify affected "recognizedRevenueByAccount()" --depth 3` traces the full consumer chain to `App()`. `graphify affected "resolveBillingAccountId()"` confirms it is also used by `grossVolumeByAccount()`, making REV-482's "gross volume ... must remain compatible" scope constraint a concrete code-level risk, not just a process note. **Real graph limitation found and verified this pass**: `graphify affected`/`explain` shows **zero edges** between `scripts/run-billing-tests.mjs` and any `billing/*` module, because the test loads them via `vite.ssrLoadModule("/src/billing/recognizedRevenue.ts")` - a runtime string path invisible to AST-based static extraction. Reading the test file directly confirms it does cover `recognizedRevenueByAccount()`, `grossVolumeByAccount()`, `loadRevenueDashboard()`, and `publishRevenueSnapshot()` (8/8 assertions passing). Anyone trusting `graphify affected` alone here would miss the one test file that matters - a documented, source-verified gap, not a false claim.
